## 目的
- 让 Windows、Linux 或其它本机不存在的必要执行环境取得与项目现有 CI 一致的验收证据，同时让发起验证前的原分支持续拥有后续工作的唯一连续性。
- 把受控验证分支限制为可审计、可回收的临时载体，避免它演变成新的长期工作分支或引入不必要的合并历史。

## 背景
- 某些验收依赖本机没有的目标平台、toolchain 或运行环境；仅凭本机结果不能证明这些环境上的行为。
- 为触发现有云端验证而临时推送分支，不代表工作所有权应从原分支迁移，也不代表验证结束后应在临时分支继续开发。
- 云端验证所需的有限外部写入与推送原分支、删除远端分支、创建 PR、合并、打 tag 或发布具有不同后果，需要分别保持授权边界。

## 决策
- 采用: 发起非本机环境验收前的原分支是工作连续性的 owner；形成待验证提交和验证后的后续工作都以原分支为归宿。
- 采用: 只有验收确实需要本机不存在的执行环境，且当前任务已经授权必要的受控分支推送时，才创建或更新临时受控分支以推送待验证提交并触发现有 CI；本机可完成的验证继续优先在本机完成。
- 采用: 临时受控分支只承载推送和 CI，不成为新的持续工作分支。云端验证成功后，必须在原分支使用 `--ff-only` 快进到已验证提交，再在原分支继续工作；不得为回归原分支创建 merge commit。
- 采用: 云端验证遵循现有 CI 和验证契约，受控分支及其提交范围只包含形成所需证据的最小改动；云端结果只证明对应环境，不放宽其它验收要求。
- 采用: 发起或观察受控云端路径时使用本地 `gh`；本地 `gh` 不存在或不可用即保持阻塞，不自行改用其它 API、网页自动化、凭据或远端写入方式。
- 采用: 必要受控分支推送之外的外部写入不自动获得授权。推送原分支、删除本地或远端临时分支、创建或合并 PR、修改 CI、打 tag、发布及其它远端变更，都必须取得各自动作所需的明确授权。
