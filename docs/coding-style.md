# Docnav 实现代码规范

本文档是 Docnav 实现代码通用质量规则的 owner，适用于行为契约已经由协议、CLI、adapter、ref、schema、输出或测试主规范明确的实现工作。它负责约束实现归属、模型选择、边界与失败、类型、代码组织和验证；具体产品行为继续由对应主规范拥有。

读者是修改 Rust 代码、TypeScript 脚本或相关测试的实现者、AI coding agent 和 reviewer。先按[文档导航](navigation.md)读取当前任务的行为 owner，再按本文的顺序约束实现取舍和交付检查。

本文聚焦可复用的实现性质：行为契约和责任边界明确后，怎样选择、组织和验证实现。具体模块名、函数名和重构方案由当前实现归属决定。

## 1. 使用顺序与权威边界

实现判断按以下优先级恢复：

1. 行为 owner 定义“系统必须做什么、由哪个组件负责、对外如何观察”。
2. 组件契约和已经确认的算法不变量可以进一步限定局部实现模型。
3. 本文承接前两者留出的通用实现取舍，提供跨组件的质量规则。
4. 当前源码和相邻惯例用于恢复实现事实；出现差异时，由行为 owner 决定目标语义。

开始实现前，按改动影响面确认以下问题。当前 owner 和实现位置已经给出答案时，直接沿用这些答案并保持改动局部：

1. 哪份主规范定义本次行为？
2. 哪个组件、模块、文件或脚本负责实现？
3. 输入、输出、状态、副作用和失败跨过哪些边界？
4. 哪些证据能够证明受影响边界仍成立？

规则来源或实现归属需要确认时，先澄清边界；其余局部取舍按本文继续。简单局部修改保持局部决策即可。

通过标准：reviewer 能从改动说明和代码位置恢复规则 owner、实现归属、影响边界和验证证据；新增模型、依赖或共享层时，还能指出它承接的当前义务。

## 2. 确定规则 owner 与实现归属

规则 owner 是行为或约束的权威来源；实现归属是承载代码的组件、模块、文件或脚本。两者各自承担明确职责，并保持对齐。

新增逻辑进入最明确的现有实现归属。新增文件、模块、crate 或共享层以清楚的职责、变化原因、复用边界或命名空间为准入条件。

现有单元能够直接承接当前义务时，优先在原实现归属内完成。文件或函数长度、质量告警、结构对称和潜在复用用于提示 reviewer 复核边界；职责、变化原因或共享契约稳定后，再据此拆分或抽象。

跨实现归属协作使用行为 owner 定义的边界、显式类型或稳定输出。调用入口承担本入口拥有的解析、校验、归一化、组合和映射；下游拥有的 opaque 值或业务语义由调用方保持原样传递。

共享代码承接多个实现归属共同依赖的稳定不变量、数据结构或错误映射，并拥有清楚命名和验证入口。准入依据是当前共享责任及其消费者。

通过标准：新增或修改的代码能够回答“哪份规则定义行为、哪段代码负责实现、谁消费结果、谁负责失败反馈”。

## 3. 按当前义务选择最小实现模型

优先路径是复用当前实现归属中的直接结构。当前契约需要更明确的状态、顺序、生命周期、变化轴或失败语义时，选择能够直接表达这些义务的最小模型。下表按实际出现的问题提供决策参考。

候选实现按以下门槛收敛：

1. 必须完整交付当前 owner 已声明、调用方能够观察的行为。
2. 每个新增抽象、分支、文件、依赖和测试都对应当前消费者、稳定契约或已确认风险。
3. 优先覆盖现实输入和失败、兼容性、安全、数据丢失及破坏性操作边界；类型和当前调用链已经封闭的私有状态沿用既有不变量。
4. 最小正确方案通过匹配验证后即可交付。验收以当前契约和验证证据为准；零告警、结构对称等指标保留为复核信号。

一个任务包含多种问题形态时，模型组合以清楚的职责边界和当前义务为依据。

| 问题形态 | 优先实现模型 | 期待性质与适用边界 |
| --- | --- | --- |
| 无状态计算和数据转换 | 纯函数与显式组合 | 输入输出直接，推理和验证保持局部；wrapper 用于承接稳定契约 |
| 有固定顺序、副作用或资源生命周期的工作流 | 结构化线性过程与局部状态 owner | 顺序、中间结果、清理和失败映射连续可见；Rust 资源优先用所有权和 RAII，事务用于真实提交或回滚边界 |
| 取值和分支集合封闭，结果只由当前值决定 | 枚举或判别联合与穷尽分支 | 边界开放值先归一化，未知值进入明确错误；归一后的封闭类型穷尽全部 variant，使新增取值直接可见 |
| 多个真实实现共享同一完整职责并需要持续替换 | trait、interface 或策略 | 消费契约稳定，差异和私有状态留在各实现；准入证据包括多个当前实现和稳定替换需求 |
| 同构且差异主要是数据的一组规则、字段、任务或映射 | typed catalog、表驱动或声明式定义 | 唯一性、引用、binding、互斥、顺序和合法值在执行前归一并校验；schema 用于序列化形状本身构成契约的场景 |
| 已标准化的外部格式、grammar 或数据契约 | 成熟 parser 或 validator 加窄适配层 | 成熟实现负责完整 grammar 和标准语义；scanner 或预处理层补充 parser API 之外的源码事实、边界或保真语义 |
| 数据关系、访问模式或复杂度约束主导实现 | 与工作负载匹配的数据结构和算法 | 有序序列用 `Vec` 或 array，唯一性用 set，按 key 查找用 map，可观察确定性需要显式顺序；外部专用结构需要真实规模、复杂度或语义证据 |

### 3.1 Rust 与 TypeScript 的落点

表中的模型语义跨语言共享，具体表达服从各自类型系统、运行时和项目约束。

- Rust 使用 `Result`、`Option`、枚举、穷尽 `match`、所有权和 RAII；局部无状态转换可以使用 iterator，共享游标或转移状态保持显式循环和状态 owner。
- TypeScript 遵循[工程工具链的 erasable TypeScript 约束](tooling.md#typescript-脚本)，优先使用 `as const`、string 或判别联合、plain object、typed callback、原生集合操作和结构化过程；class 或 wrapper 用于承接明确的对象身份或稳定契约。

语言原生能力已经完整承接问题时，以原生能力作为最终实现。

### 3.2 外部库与共享抽象准入

外部格式、grammar、schema、密码学、tokenization 和其它完整正确性表面较大的标准能力，优先复用项目已经选择的成熟实现。需要新增任何外部依赖时，同时满足以下条件后才进入实现：

1. 真实任务已经暴露语言原生能力或现有依赖的缺口。
2. 候选能够降低总体实现、认知、升级和验证成本；样板缩减在确实降低这些成本时计入收益。
3. 目标组件能够承担库的语义使用、错误映射和失败反馈。
4. 对应 manifest 和[工程工具链](tooling.md)明确版本、安装与运行边界。
5. 项目验证入口覆盖当前运行时、类型系统、输出和错误边界。

依赖选择以当前语义、owner 和总体维护成本为依据。项目能力文档记录已经采用并验证的依赖。

扩大共享 adapter trait 或其它跨 adapter 抽象时，继续遵循[架构](architecture.md)和[适配器契约](adapter-contract.md)的异构实现证据门槛；领域 owner 已定义的准入条件保持生效。

通过标准：实现者能说明主导问题形态、所选模型如何兑现对应期待、不同模型为何在当前边界组合，以及新增依赖或共享抽象对应什么真实义务。

## 4. 在边界完成解析与失败映射

用户输入、CLI 参数、配置、路径、文件系统、进程、JSON、schema 和 adapter 输出都属于边界。边界数据按同一方向流动：

1. 未经信任的外部值进入边界。
2. 边界完成解析、校验和归一化。
3. 内部逻辑接收已经归一化的领域对象。
4. 入口把结果或失败映射为稳定输出、诊断和退出状态。

边界失败向调用方提供与入口相符的行动信息：

- 产品入口返回稳定错误、明确退出码或可行动诊断。
- 验证脚本指出文件、字段或规则及失败原因。
- 机器输出和诊断输出保持各自通道职责。

默认值、格式推断、跳过和恢复策略由行为 owner 明确定义，并保留足够定位证据。边界失败映射为稳定错误或可行动诊断；可恢复兜底遵循主规范定义的输出层规则。

防御性校验由接收外部输入的边界 owner 完成。值归一化为封闭类型后，下游将该结果作为已建立的不变量使用。

通过标准：任何失败路径都能回答“调用方下一步该查看、修改或重试什么”，且每个值在所属边界完成一次解析和归一化。

## 5. 用类型表达领域含义

跨模块传递领域含义时，使用能够表达业务含义和不变量的类型。协议镜像、opaque options、错误 details、脚本校验和局部 glue code 可以使用裸字符串、通用 JSON 值或元组。

类型设计遵循以下规则：

1. 协议镜像类型表达稳定序列化形状；格式私有语义留在对应 adapter。
2. 领域逻辑入口接收已经校验和归一化的值，并直接应用领域语义。
3. 公开 API 通过类型化返回值表达普通失败。
4. 稳定字段、operation、错误码、退出码、schema 名和诊断前缀使用枚举、新类型、职责内常量或配置表达，并归入对应 owner。

按失败语义选择表示：

| 语义 | 表示与边界 |
| --- | --- |
| 缺失是合法结果，调用方无需原因 | 使用 `Option`、`null`、`undefined` 或等价类型 |
| 调用方需要区分失败类别、携带结构化定位或据此恢复 | 使用 `Result`、判别结果或稳定错误类型 |
| 失败只终止当前 TypeScript 维护脚本，入口负责统一生成可行动诊断 | 可以在组件边界内抛出 `Error`；承诺稳定 code、字段或机器映射时使用对应稳定错误类型 |
| Rust 生产代码中的程序不变量被破坏 | `panic`、`expect` 或不可达断言用于局部代码已经证明的不变量，并在消息中写明该不变量 |

测试 fixture、一次性局部标签和单个小作用域内的示例数据可以直写；稳定规则、跨边界字段和错误映射集中在对应 enum、newtype、owner 常量或配置中。

`scripts/` 和 `test/` 下跨模块传递的任务配置、schema 结果、进程结果、质量观测和 smoke state 使用显式 TypeScript 类型；脚本语法、文件扩展名和类型检查入口由[工程工具链](tooling.md)拥有。

通过标准：函数签名能够区分原始输入、协议字段、领域对象、格式私有参数、合法缺失和可恢复失败。

## 6. 按变化原因组织文件与模块

文件、模块、函数和脚本围绕一个可独立说明的变化原因组织。目录方案服从当前实现归属和相邻模块惯例；固定行数或圈复杂度用于提示复核边界。

父模块专用的 helper、wrapper、常量和小类型留在父模块附近。多个同级文件依靠共同前缀表达分组时，优先使用目录或模块表达该分组；项目惯例、外部契约、生成规则或测试编号要求可以保留现有形态。

拆分后每个单元都应获得更清楚的责任、消费者或独立验证边界。helper 和测试 fixture 在共享责任成立时拆分；父模块专用内容继续靠近父模块。

Rust 模块入口采用“同名入口文件 + 同名目录”，例如由 `reader.rs` 组织 `reader/` 子模块；`lib.rs`、`main.rs` 等 crate root 按 Rust 约定保留。

出现以下信号时重新判断边界：

1. 同一单元同时承载多个组件职责、输出边界或边界类型。
2. 新功能持续要求修改无关代码。
3. 解析、领域判断、文件操作、输出或错误映射互相遮蔽。
4. reviewer 需要列举多个彼此独立的职责才能说明该单元。

通过标准：路径和命名能够表达实现归属；局部改动的阅读范围集中在受影响组件、流程和输出边界。

## 7. 让稳定规则回到唯一 owner

主规范和 schema 拥有稳定规则；代码和验证脚本实现或校验规则；示例证明语义和字段形状。

实现发现规则缺失、冲突或过期时，按以下位置处理：

| 规则面 | Owner |
| --- | --- |
| 产品职责、协议语义、输出语义和 adapter 契约 | [文档导航](navigation.md)指向的对应主规范 |
| JSON 字段形状 | 对应 schema；示例承载示例语义和一致性证据 |
| 测试层级、覆盖目标和 Case 归属 | 测试规范与 Case 账本 |
| 脚本语言、包管理、依赖运行和验证入口 | [工程工具链](tooling.md) |

涉及 contract surface 时，按影响面同步主规范、schema、示例、代码和验证材料，并在交付说明中记录同步范围。

通过标准：任何稳定规则变化都能指出唯一 owner，并说明本次同步了哪些受影响材料。

## 8. 按风险选择验证层级

验证随影响面扩展，目标是证明受影响边界仍成立；编译和静态检查是第一层证据。

1. 内部计算、解析或映射语义使用单元测试、fixture 或等价局部验证证明不变量。
2. 入口行为使用集成测试或等价命令验证成功、失败、退出状态和输出通道。
3. schema、示例和 machine output 保持可编译、可解析并能互相映射。
4. 文件系统、进程、生成和输出层改动覆盖路径、失败恢复、确定性及 stdout/stderr 边界。
5. 纯文档改动至少使用 `dnm outline`、局部 diff 或等价方式确认结构和范围。
6. 受环境限制的验证在交付说明中写明原因、待验证边界和残余风险。

测试的可观察性、等价类和 Case 粒度由[测试策略](testing.md)拥有，生产接口来自产品消费者。质量工具的 warning 用于定位风险；correctness、maintainability 和 owner 证据共同决定接受、记录或调整实现。

具体命令由[工程工具链](tooling.md)、[测试策略](testing.md)和项目指令拥有。

通过标准：验证证据与本次改动的行为、边界、失败和同步材料一一对应。

## 9. 变更前后自检

实现前先按影响面完成第 1—2 项，明确 owner 与实现归属；需要改变实现模型时再展开模型比较。实现中使用与改动有关的第 3—7 项；交付前检查适用于本次改动的项目，其余表面沿用现有证据：

1. 行为 owner、实现归属、当前消费者和受影响边界是否明确？
2. 实现是否选择了最直接的正确方案；新增抽象、分支、文件、依赖和测试能否对应当前义务？
3. 边界是否在所属位置完成一次解析、校验和归一化，类型与失败是否给调用方足够信息？
4. 文件、模块和共享代码是否对应真实变化原因或共享职责，指标是否只作为复核输入？
5. 稳定规则是否只有一个 owner，contract surface 是否只同步受影响材料？
6. 验证是否用代表性、可观察证据覆盖受影响行为、错误和输出边界？
7. 受环境限制的验证和仍然存在的现实风险是否已明确？
