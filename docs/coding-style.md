# Docnav 实现代码规范

本文档是 Docnav 实现代码通用质量规则的 owner。它约束实现归属、模型选择、边界与失败、类型、代码组织和验证，不定义产品行为，也不替代协议、CLI、adapter、ref、schema、输出或测试规范。

读者是修改 Rust 代码、TypeScript 脚本或相关测试的实现者、AI coding agent 和 reviewer。先按[文档导航](navigation.md)读取当前任务的行为 owner，再按本文的顺序约束实现取舍和交付检查。

本文不预设具体模块名、函数名或重构方案。它只回答：在已经明确行为契约和责任边界后，实现代码应该保持什么性质。

## 1. 使用顺序与权威边界

实现判断按以下优先级恢复：

1. 行为 owner 定义“系统必须做什么、由哪个组件负责、对外如何观察”。
2. 组件契约和已经确认的算法不变量可以进一步限定局部实现模型。
3. 本文在前两者没有更具体约定时，提供跨组件的通用实现规则。
4. 当前源码和相邻惯例用于恢复现状，不能覆盖行为 owner 或把历史写法自动提升为规范。

开始实现前，先回答五个问题：

1. 哪份主规范定义本次行为？
2. 哪个组件、模块、文件或脚本负责实现？
3. 当前职责的主导问题形态是什么？
4. 输入、输出、状态、副作用和失败跨过哪些边界？
5. 哪些证据能够证明受影响边界仍成立？

无法回答规则来源或实现归属时，先澄清边界；其余不会改变目标或责任的局部取舍，按本文继续。

通过标准：reviewer 能从改动说明和代码位置恢复规则 owner、实现归属、所选模型、影响边界和验证证据。

## 2. 确定规则 owner 与实现归属

规则 owner 是行为或约束的权威来源；实现归属是承载代码的组件、模块、文件或脚本。两者必须对齐，但不是同一个对象。

新增逻辑进入最明确的现有实现归属。只有职责、变化原因、复用边界或命名空间已经清楚时，才新增文件、模块、crate 或共享层。

跨实现归属协作使用行为 owner 定义的边界、显式类型或稳定输出。调用入口只承担本入口拥有的解析、校验、归一化、组合和映射；下游拥有的 opaque 值或业务语义原样传递，不在调用方重新生成、解析或判断。

共享代码只承接多个实现归属真正共享的不变量、数据结构或错误映射，并拥有清楚命名和验证入口。调用位置相似、代码较短或将来可能复用，都不足以绕过原实现归属。

通过标准：新增或修改的代码能够回答“哪份规则定义行为、哪段代码负责实现、谁消费结果、谁负责失败反馈”。

## 3. 按问题形态选择实现模型

先识别当前职责的合法状态、顺序或生命周期、变化轴和失败语义，再选择能够直接表达这些义务的最小模型。一个任务包含多种问题形态时，只在职责边界清楚的位置组合模型。

| 问题形态 | 优先实现模型 | 期待性质与适用边界 |
| --- | --- | --- |
| 无状态计算和数据转换 | 纯函数与显式组合 | 输入输出直接，推理和验证保持局部；额外 wrapper 必须承接稳定契约，而不是只改变调用外观 |
| 有固定顺序、副作用和失败传播的工作流 | 结构化线性过程 | 顺序、中间结果、资源清理和失败映射连续可见；只有存在真实提交或回滚边界时使用事务，依赖、互斥或并发本身是输入时才使用经验证的 task graph 或 scheduler |
| 取值和分支集合封闭，结果只由当前值决定 | 枚举或判别联合与穷尽分支 | 边界开放值先归一化，未知值进入明确错误；归一后的封闭类型显式覆盖全部 variant，不用兜底分支掩盖新增取值 |
| 行为取决于当前状态和事件，合法转移需要约束 | 显式状态、事件与转移模型 | 状态、事件、guard、非法转移和终止条件可以检查；普通条件分支、accumulator 或单向阶段不升级为状态机 |
| 对象具有稳定身份、生命周期或持续不变量 | 状态 owner 与受控操作 | 状态和行为位于同一责任边界，构造、访问、变更和释放不能绕过不变量；TypeScript 不因此必须使用 class |
| 多个真实实现共享同一完整职责并需要持续替换 | trait、interface 或策略 | 消费契约稳定，差异和私有状态留在各实现；单一实现、仅调用位置相似或假想扩展不建立抽象 |
| 同构且差异主要是数据的一组规则、字段、任务或映射 | typed catalog、表驱动或声明式定义 | 唯一性、引用、binding、互斥、顺序和合法值在执行前归一并校验；只有序列化形状本身是契约时才使用 schema |
| 已标准化的外部格式、grammar 或数据契约 | 成熟 parser 或 validator 加窄适配层 | 成熟实现负责完整 grammar 和标准语义；scanner 或预处理层只补充 parser 不提供的源码事实、边界或保真语义 |
| 数据经过多个可独立复用或验证的稳定阶段 | 类型化流水线 | 每个阶段拥有明确输入、输出和失败边界；单一线性流程保持结构化过程，共享游标、资源或事务不变量留在同一 owner |
| 数据关系、访问模式或复杂度约束主导实现 | 与工作负载匹配的数据结构和算法 | 有序序列用 `Vec` 或 array，唯一性用 set，按 key 查找用 map，可观察确定性需要显式顺序；外部专用结构需要真实规模、复杂度或语义证据 |

### 3.1 Rust 与 TypeScript 的落点

表中的模型语义跨语言共享，具体表达服从各自类型系统、运行时和项目约束。

- Rust 使用 `Result`、`Option`、枚举、穷尽 `match`、所有权和 RAII；局部无状态转换可以使用 iterator，共享游标或转移状态保持显式循环和状态 owner。
- TypeScript 遵循[工程工具链的 erasable TypeScript 约束](tooling.md#typescript-脚本)，使用 `as const`、string 或判别联合、plain object、typed callback、原生集合操作和结构化过程；不为模仿 Rust 类型或抽象而增加 class 或 wrapper。

语言原生能力已经完整承接问题时，不增加宏、框架或第三方库。

### 3.2 外部库与共享抽象准入

外部格式、grammar、schema、密码学、tokenization 和其它完整正确性表面较大的标准能力，优先复用项目已经选择的成熟实现。需要新增任何外部依赖时，同时满足以下条件后才进入实现：

1. 真实任务已经暴露语言原生能力或现有依赖的缺口。
2. 候选能够降低总体实现、认知、升级和验证成本，而不只是减少少量样板或提供另一种链式写法。
3. 目标组件能够承担库的语义使用、错误映射和失败反馈。
4. 对应 manifest 和[工程工具链](tooling.md)明确版本、安装与运行边界。
5. 项目验证入口覆盖当前运行时、类型系统、输出和错误边界。

已经安装的库不自动成为相邻代码的首选风格；尚未采用的候选不写成当前项目能力或动态安装提示。

扩大共享 adapter trait 或其它跨 adapter 抽象时，继续遵循[架构](architecture.md)和[适配器契约](adapter-contract.md)的异构实现证据门槛；本节不降低领域 owner 已定义的准入条件。

通过标准：实现者能说明主导问题形态、所选模型如何兑现对应期待、不同模型为何在当前边界组合，以及新增依赖或共享抽象对应什么真实义务。

## 4. 在边界完成解析与失败映射

用户输入、CLI 参数、配置、路径、文件系统、进程、JSON、schema 和 adapter 输出都属于边界。边界数据按同一方向流动：

1. 未经信任的外部值进入边界。
2. 边界完成解析、校验和归一化。
3. 内部逻辑只接收已经归一化的领域对象。
4. 入口把结果或失败映射为稳定输出、诊断和退出状态。

边界失败向调用方提供与入口相符的行动信息：

- 产品入口返回稳定错误、明确退出码或可行动诊断。
- 验证脚本指出文件、字段或规则及失败原因。
- 机器输出和诊断输出保持各自通道职责。

默认值、格式推断、跳过和恢复策略只有在行为 owner 明确定义时才使用，并保留足够定位证据。不能通过空结果、默认 adapter、默认 ref、猜测 content type 或静默跳过掩盖失败；可恢复兜底必须映射到主规范定义的输出层规则。

通过标准：任何失败路径都能回答“调用方下一步该查看、修改或重试什么”，且边界内没有重复解析已经归一化的值。

## 5. 用类型表达领域含义

跨模块传递领域含义时，使用能够表达业务含义和不变量的类型。裸字符串、通用 JSON 值和元组只适合协议镜像、opaque options、错误 details、脚本校验和局部 glue code。

类型设计遵循以下规则：

1. 协议镜像类型保持稳定序列化形状，不吸收格式私有语义。
2. 领域逻辑入口只接收已经校验的值，不重复解析原始输入。
3. 公开 API 通过返回值表达普通失败，不因调用方可传入的普通非法值 panic。
4. 稳定字段、operation、错误码、退出码、schema 名和诊断前缀使用枚举、新类型、职责内常量或配置表达，不进入跨组件的杂物常量池。

按失败语义选择表示：

| 语义 | 表示与边界 |
| --- | --- |
| “没有值”是合法结果，调用方不需要原因 | 使用 `Option`、`null`、`undefined` 或等价类型 |
| 调用方需要区分失败类别、携带结构化定位或据此恢复 | 使用 `Result`、判别结果或稳定错误类型 |
| 失败只终止当前 TypeScript 维护脚本，入口负责统一生成可行动诊断 | 可以在组件边界内抛出 `Error`；已承诺稳定 code、字段或机器映射的失败不得擦除为通用异常 |
| Rust 生产代码中的程序不变量被破坏 | 只有局部代码已经证明不变量时才使用 `panic`、`expect` 或不可达断言，并在消息中写明不变量 |

测试 fixture、一次性局部标签和单个小作用域内的示例数据可以直写，但稳定规则、跨边界字段和错误映射不能散落为魔法值。

`scripts/` 和 `test/` 下跨模块传递的任务配置、schema 结果、进程结果、质量观测和 smoke state 使用显式 TypeScript 类型；脚本语法、文件扩展名和类型检查入口由[工程工具链](tooling.md)拥有。

通过标准：函数签名能够区分原始输入、协议字段、领域对象、格式私有参数、合法缺失和可恢复失败。

## 6. 按变化原因组织文件与模块

文件、模块、函数和脚本围绕一个可独立说明的变化原因组织。目录方案服从当前实现归属和相邻模块惯例，不由固定行数或圈复杂度决定。

只服务一个父模块的 helper、wrapper、常量和小类型留在父模块附近。多个同级文件只能依靠共同前缀表达分组时，优先使用目录或模块表达该分组；项目惯例、外部契约、生成规则或测试编号要求可以保留现有形态。

Rust 模块优先使用“同名入口文件 + 同名目录”，例如由 `reader.rs` 组织 `reader/` 子模块。新增模块入口不使用 `mod.rs`；`lib.rs`、`main.rs` 等 crate root 按 Rust 约定保留。

出现以下信号时重新判断边界：

1. 同一单元同时承载多个组件职责、输出边界或边界类型。
2. 新功能持续要求修改无关代码。
3. 解析、领域判断、文件操作、输出或错误映射互相遮蔽。
4. reviewer 无法用一个简短句子说明该单元的主职责。

通过标准：路径和命名能够表达实现归属；局部改动不要求读者同时理解无关组件、流程或输出边界。

## 7. 让稳定规则回到唯一 owner

代码和验证脚本实现或校验规则，不成为新的规则来源；示例证明语义和字段形状，不替代主规范或 schema。

实现发现规则缺失、冲突或过期时，按以下位置处理：

| 规则面 | Owner |
| --- | --- |
| 产品职责、协议语义、输出语义和 adapter 契约 | [文档导航](navigation.md)指向的对应主规范 |
| JSON 字段形状 | 对应 schema；示例只承载示例语义和一致性证据 |
| 测试层级、覆盖目标和 Case 归属 | 测试规范与 Case 账本 |
| 脚本语言、包管理、依赖运行和验证入口 | [工程工具链](tooling.md) |

涉及 contract surface 时，只按影响面同步主规范、schema、示例、代码和验证材料。未受影响的材料不为“保持一致”而复制规则。

通过标准：任何稳定规则变化都能指出唯一 owner，并说明本次同步了哪些受影响材料。

## 8. 按风险选择验证层级

验证随影响面扩展，目标是证明受影响边界仍成立，而不只是证明代码能够编译。

1. 内部计算、解析或映射语义使用单元测试、fixture 或等价局部验证证明不变量。
2. 入口行为使用集成测试或等价命令验证成功、失败、退出状态和输出通道。
3. schema、示例和 machine output 保持可编译、可解析并能互相映射。
4. 文件系统、进程、生成和输出层改动覆盖路径、失败恢复、确定性及 stdout/stderr 边界。
5. 纯文档改动至少使用 `dnm outline`、局部 diff 或等价方式确认结构和范围。
6. 无法运行的验证在交付说明中写明原因、未覆盖边界和残余风险。

具体命令由[工程工具链](tooling.md)、[测试策略](testing.md)和项目指令拥有。

通过标准：验证证据与本次改动的行为、边界、失败和同步材料一一对应。

## 9. 变更前后自检

实现前先完成第 1—2 项，明确 owner、实现归属和模型；实现中按第 3—7 项约束边界；交付前按以下顺序完成全部检查：

1. 是否已找到行为 owner，并把代码放到明确实现归属？
2. 所选模型是否直接表达当前合法状态、顺序或生命周期、变化轴和失败语义？
3. 边界是否只解析、校验和归一化一次，失败是否提供可行动反馈？
4. 类型是否区分原始输入、领域对象、合法缺失、可恢复失败和稳定机器错误？
5. 同一不变量是否避免无理由的多套表达，不同表达是否由稳定语义差异支撑？
6. 文件和模块是否围绕独立变化原因组织，共享代码是否承接真实共享职责？
7. 新增依赖或共享抽象是否对应真实能力缺口，并落到已有组件、manifest、工具链和验证边界？
8. 稳定规则是否只有一个 owner，contract surface 是否只同步受影响材料？
9. 验证是否覆盖受影响行为、错误路径、输出通道和无法执行的残余风险？
