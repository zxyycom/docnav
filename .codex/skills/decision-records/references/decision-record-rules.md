# 决策记录领域契约

本文面向需要创建、修订或维护决策记录的 agent，定义决策模型及写入时必须保持的语义和安全不变量。日常恢复与动作选择由 `SKILL.md` 承接；索引的精确机器结构由 [decision-index.schema.json](decision-index.schema.json) 承接；当前 CLI 参数、输出和退出状态以 `scripts/decision-records.mjs --help` 及实际诊断为准。

## 权威来源与职责

1. `SKILL.md` 决定 agent 何时恢复决策、如何判断当前任务以及何时进入维护。
2. 本契约决定什么是合法决策、领域和身份如何表达、生命周期与关系如何演进、版本快照如何隔离，以及写入必须满足什么条件。
3. `decision-domains.json` 是领域定义来源；每条决策 Markdown 是自身内容、生命周期、对齐状态和关系的来源。
4. `decision-index.json` 是从权威来源建立的持久查询快照，不拥有独立决策状态，也不作为领域或 Markdown 的反向修复来源。
5. 代码、配置、规范和项目文档是当前事实来源。决策记录保存长期方向和理由，不复制当前实现、任务进度或执行日志。
6. 本契约中的“内容 owner”只表示某项规则应由哪个文档完整承接；判断决策是否落实时以“当前事实来源”为准。

## 决策集合与稳定身份

未传 `--decisions-dir` 时，决策根目录是 `<root>/docs/decisions`；显式相对路径只相对 `--root` 解析，绝对路径直接作为决策根目录。决策集合不要求位于 Git 仓库。

```text
<decision-root>/
├── decision-domains.json
├── decision-index.json
└── <domain-id>/
    └── <semantic-slug>.md
```

1. 根目录只保存领域目录表、派生索引和已定义的一级领域目录；归档记录仍留在原领域，不建立物理归档目录。
2. 每条 Markdown 直接位于一个领域目录。未知目录、嵌套目录、领域目录中的非 Markdown 文件和已经存在但为空的领域目录均无效。
3. `<domain-id>/<semantic-slug>.md` 是稳定身份。文件名使用简短 kebab-case 语义名称，不包含日期、状态或一次性动作。
4. 路径第一段是唯一领域归属。领域纠正或结构迁移必须同时更新路径、全部关系目标、直接引用和派生索引。

## 版本快照与 pending 决策范围

`stage` 在不改变决策生命周期的前提下，从三个彼此独立的状态构造待提交集合：

1. `revision` 是命令开始时当前已提交的不可变版本，也是已有决策集合的基线。
2. `filesystem` 是命令运行时磁盘上的决策文件集合。生命周期命令、手工编辑和磁盘索引维护直接读写这些文件；它们本身不读取或判断 `pending`。
3. `pending` 是准备进入下一版本的版本管理快照。它不是决策成员、生命周期、对齐状态、关系或查询索引的事实来源。

`stage <decision-path...>` 的目标决策源集合固定按以下规则构造：

1. 调用方至少显式选择一个决策根相对 POSIX Markdown 路径。命令不从关系、差异、时间或此前命令自动扩展选择集。
2. 目标以完整 `revision` 决策源集合为基线，只叠加所选路径在 `filesystem` 中的存在状态。路径只在磁盘存在表示新增或替换；只在 `revision` 存在表示删除；两处都不存在表示输入无效。重命名由旧路径删除和新路径新增这两个显式选择共同表达。
3. 已有 `revision` 决策范围时，目标固定使用其中的 `decision-domains.json`，忽略它在 `filesystem` 或既有 `pending` 中的变化。所选决策依赖该目录表之外的领域时，目标无效。
4. 当前 `revision` 尚无任何决策范围成员时，首次集合使用完整、合法的 `filesystem` 领域目录表并以空的 revision 决策集合为基线；目标仍必须至少包含一条已建立决策。首版不选择或合并领域目录表的局部变化。
5. 目标中的领域目录表、全部已建立 Markdown 与 `decision-index.json` 必须来自同一目标来源。索引使用完整目标集合重建并通过领域、生命周期、关系、成员和 `sourceRevision` 校验；`filesystem` 或既有 `pending` 中的索引都不是构造输入。

`pending` 决策范围包含决策根内的领域目录表、全部已建立决策 Markdown 和完整派生索引，并作为一个整体替换：

1. 最后一次成功的 `stage` 调用决定完整 `pending` 决策范围；此前位于该范围内但未被本次目标包含的变化恢复为 `revision` 状态。
2. 决策范围外的既有 `pending` 内容保持不变；完整 `filesystem` 保持不变。因此成功后 `filesystem` 索引与 `pending` 索引可以有意不同。
3. `activate`、`evolve`、`mark-aligned`、`archive`、`discard`、`sync-index` 和 `check` 直接维护或验证磁盘决策文件；这些命令没有 `pending` 分支，不读取、合并或写入 `pending`，也不提供 `--stage`。

目标来源在任何 `pending` 写入前完成校验。非法或重复路径、缺失路径、候选、未知领域、非法关系、不可用版本管理环境均不得产生待提交写入。构造后若 `revision` 或受控 `pending` 前提已经变化，命令以冲突失败且不接受陈旧替换；调用方重新读取当前状态后重试。替换过程对可处理失败恢复原决策范围，恢复无法完成或核对时停止并报告范围可能不完整。

当前分发实现仅支持 Git 工作区，但领域契约、共享版本管理边界和 CLI 结果只使用上述项目级快照、路径与失败语义；这不表示其他版本管理后端已经实现，也不允许向公共结果透传 Git 命令、index、对象、模式或锁等内部信息。

## 受控领域

`decision-domains.json` 使用以下最小结构：

```json
{
  "schemaVersion": 1,
  "domains": [
    {
      "id": "workflow-governance",
      "description": "维护工作流中的批准、责任和长期治理边界。"
    }
  ]
}
```

1. `domains` 非空并按 `id` 升序排列；ID 是唯一 kebab-case 名称，描述用单行文本界定一个稳定责任或能力边界。
2. 一条决策选择拥有被改变契约的主要领域，不按正文中出现的名词、执行阶段或所有受影响对象归类。
3. 可以独立修订、替代或退役的跨领域判断分别记录；其他影响写入正文，不建立自由 tag 或 `impact` 字段。
4. CLI 的 `domains` 命令只读展示领域。新增领域或修改描述时直接编辑目录表；新增但尚无记录的领域不创建空目录。
5. 删除领域前必须确认没有决策路径继续使用该 ID。重命名、拆分或归并领域属于结构迁移，先处理全部路径、关系和直接引用，达到长期维护门槛时另行记录决策。
6. 领域变化后运行 `sync-index --write` 和严格 `check`；不得直接修改索引中的领域 metadata。

## 什么进入决策记录

只有同时满足以下条件的判断才进入记录：

1. 它会持续影响后续行为、责任边界、兼容性、风险处理或验收。
2. 缺少记录时，未来难以恢复为何采用当前方向。
3. 它是完整到可以接受语义审核的判断或取舍，而不是事实、任务、进度或执行结果。
4. 它能够作为一个整体被独立修订、替代、判定无效、归并、归档和判断对齐。

满足上述门槛但尚未审核确认的方向使用 `candidate`；只有审核通过的判断才能成为活动记录。一条活动记录必须能够独立表达当前判断，不要求读者拼接前序。目的说明希望长期达成什么，背景说明为何需要选择，决策说明采用方向、核心理由以及必须长期遵守的限制、允许范围或例外。

已经确认但尚未成为当前事实的未来方向仍属于决策，以 `active + unaligned` 表达。它为后续选择提供演进参考，不保证将来一定实施；实现步骤、排期、任务分解和进度仍由 change、计划或其他执行 owner 承接。

`alignment` 始终作用于完整决策。只有部分方向成为当前事实时，不增加部分对齐状态：不可独立演进的局部落地使整条记录继续保持 `unaligned`；可以分别修订、归档或对齐的部分说明记录过粗，应通过闭合拆分重建为多条自包含决策。

## Markdown 记录

新候选和已建立记录使用同一正文结构，并保持所示 frontmatter 与正文顺序。新候选先使用以下状态组合：

```markdown
---
title: <标题>
status: candidate
alignment: null
createdAt: null
purpose: <精简目的>
background: <精简背景>
decision: <精简采用方向>
relations: []
---

## 目的
- <希望长期达成或维护的结果>

## 背景
- <促成选择的事实、问题与关键约束>

## 决策
- 采用: <最终方向、核心理由和长期约束>
```

1. 标题和三项摘要是 4 至 100 个 Unicode 码点的单行文本；摘要不得引入对应正文没有表达的独立含义。
2. 正文只使用依次排列的 `目的`、`背景` 和 `决策` 二级章节，不重复一级标题、摘要或关系。
3. `决策` 至少包含一个非空 `采用`；关键备选确实有助于回放时可以增加 `不采用`。
4. 当前事实和实施差距不复制进正文。需要判断对齐时，将完整决策与当前事实来源比较。
5. 已建立记录的正文只允许不改变目的、范围、关键背景、采用方向或核心理由的编辑性修正；判断语义变化通过新记录和真实演进关系表达。已建立记录的 `relations` 不随正文直接编辑，只能按“关系事务与完整集合”完整修订。
6. 候选同样必须通过完整 frontmatter、摘要和三段正文校验；它可以在审核前原地修改，但不能用缺失章节、占位摘要或非法关系保存半成品。尚未达到该门槛的内容留在对话、change 或其他草稿 owner 中。
7. 模板中的 `relations: []` 只表示该候选没有直接前序。候选存在演进意图时，`relations` 保存从候选到真实直接前序的完整预期集合，与正文一起接受审核；不能为了等待建立命令而省略已经明确的关系。

## 生命周期与对齐

| 状态 | 含义 |
| --- | --- |
| `candidate + alignment: null + createdAt: null` | 结构和内容完整、可以审核，但尚未建立和生效；不进入正式索引，可以继续收敛、等待审核或安全丢弃。 |
| `active + aligned` | 决策已经确认并进入当前决策集合，完整方向已经成为当前事实并通过核对；后续相关工作必须遵守该基线。 |
| `active + unaligned` | 决策已经确认并进入当前决策集合，是尚未成为当前事实的未来方向；相关工作必须把它作为选择输入，但它不保证将来一定实施。 |
| `archived + aligned/unaligned` | 不再作为当前依据，保留归档前最后对齐状态以及理由和演进历史。 |
| 历史 `archived + alignment: null` | 不再作为当前依据，且归档前与当前事实的关系未知；只为兼容既有记录。 |

1. 首次 `activate` 是审核与建立边界：它把完整候选改为 `active`，选择非空 `alignment` 并写入不可变的建立时间；Git 提交、暂存或历史不参与建立状态。
2. `active` 表示决策已经确认并进入当前决策集合；必须结合 `alignment` 判断它是当前基线还是未来方向。
3. 未对齐方向必须作为相关工作的选择输入，但 `alignment` 本身不创建实施承诺、任务、优先级、授权或范围。当前任务如何区分“未来方向输入”和“实施未来方向”，以及兼容性微调需要满足什么条件，由 [`SKILL.md` 的“选择动作”](../SKILL.md#4-选择动作) 承接。
4. 当前任务的交付或验收目标明确包含未对齐方向的全部或一部分时，才按该方向实施；不可独立演进的部分落地仍使整条记录保持 `unaligned`，能够独立演进的部分通过闭合拆分事务重建后分别保存对齐状态。
5. 未对齐方向可以在成为当前基线前被修订或归档。它约束相关选择，但不承诺最终一定进入 `aligned`。
6. 对齐是从 `unaligned` 到 `aligned` 的单向事实基线；只有完整方向已经成为当前事实并通过核对后才能标记。部分对齐既不改变字段，也不允许直接拆改已建立正文；记录确实包含多个独立判断时，以闭合拆分事务归档粗记录并建立分别对齐的后继。已对齐记录后来与事实偏离时报告一致性问题，不把原记录改回未对齐。
7. 描述当前事实的活动已对齐基线可以与面向未来的活动未对齐方向并存，二者的差异本身不是冲突；多个当前基线彼此不能兼容、多个未来方向彼此不能兼容，或已对齐基线偏离当前事实时，才属于一致性问题。
8. 归档保留最后一个非空 `alignment`；新归档必须写入 `aligned` 或 `unaligned`，既有 `null` 只表示无法得知归档前完整方向是否已经成为当前事实。已归档记录重新激活时保留原 `createdAt` 和既有关系，并由本次激活参数建立当前对齐状态。
9. 关系字段本身不隐式改变生命周期或对齐状态；激活、演进、对齐和归档都由显式维护动作完成。
10. `candidate` 只表示尚未审核建立的完整记录，不承接已经确认但尚未执行的方向；后者使用 `active + unaligned`。Git `pending` 只表示版本快照，也不属于该生命周期。

## 演进关系

新判断改变已有决策时，在新记录中使用从新到旧的直接关系：

```yaml
relations:
  - type: 修订
    target: workflow-governance/direct-predecessor.md
```

1. `修订` 保留主体方向并改变一部分；`替代` 用完整新判断取代前序；`判定无效` 表明前序依据不成立；`归并` 把多个前序整合为一个可独立使用的当前判断；`拆分` 表示一个过粗前序被重建为多个可独立使用的后继。
2. 关系只指向直接前序；每个目标只出现一次并使用一个关系类型，不自环、不形成环。目标使用决策根目录相对 POSIX 路径，并在后继建立事务完成时处于归档状态。
3. 候选关系接受类型、路径、重复、自环和目标可解析性等前瞻性检查，但在候选建立前不进入正式关系图，也不要求活动直接前序提前归档。建立事务必须重新读取完整最终成员，并证明最终生命周期、环路和关系策略均合法。
4. 一次拆分同时归档一个活动直接前序并建立或选择至少两个后继；每条后继各保存一条指向该前序的 `拆分` 关系并拥有自己的对齐状态。任一前序只有一个 `拆分` 后继时，关系集合不闭合。
5. 拆分后的每条记录必须自包含，完整后继集合必须覆盖前序中继续有效的全部长期含义；被放弃、改写或判定无效的部分也要明确交代，不能通过归档前序静默丢失。该语义覆盖由 agent 审阅，CLI 只机械证明成员、数量、生命周期、关系和事务闭合。
6. 关系只保存真实语义演进，不作为分类、引用列表、任务依赖或实施映射。当前 `归并` 与 `拆分` 分别承接多对一和一对多；没有现实实例时不为多对多重组新增推测性关系。

## 关系事务与完整集合

`evolve` 是关系建立、完整修订和闭合后继集合变化的统一事务入口。一次事务使用以下稳定术语：

- **所选后继**：本次调用通过重复 `--successor <alignment=decision-path>` 显式选择的全部候选或已建立记录；路径规范化后必须互不重复。
- **来源关系**：每个所选后继 Markdown 当前保存的完整 `relations`。
- **关系覆盖**：本次调用通过重复 `--relation <type=decision-path>` 显式提供的全部关系，或由 `--clear-relations` 表达的空集合；同一覆盖作用于全部所选后继。
- **有效最终关系**：按来源关系和关系覆盖解析后，准备写入并参与策略及最终图校验的每个后继完整关系集合。

关系来源按以下优先级解析；覆盖始终完整替换来源关系，不做逐边追加、合并或继承：

| 调用方关系输入 | 每个所选后继的有效最终关系 |
| --- | --- |
| 一个或多个 `--relation` | 使用同一组规范化后的非空关系覆盖。 |
| `--clear-relations` | 使用空集合。 |
| 两者均未提供 | 分别使用该后继自身的来源关系。 |

1. `--relation` 与 `--clear-relations` 互斥；“未提供覆盖”和“显式空集合”是不同意图。路径规范化后重复的覆盖关系在写入前失败。
2. `evolve` 至少选择一个后继，并为每个后继提供对齐选择。候选以该选择建立；已建立记录只接受与现有非空 `alignment` 一致的确认值，其正文、`status`、`alignment` 和 `createdAt` 保持不变，只有完整关系集合可以变化。历史 `archived + alignment: null` 不进入普通关系修订。
3. `activate` 只显式选择一个目标。新候选没有有效关系时执行普通建立；候选自身声明关系，或调用方提供 `--relation` 或 `--clear-relations` 时，目标进入同一个单后继关系事务。重新激活已归档记录时保留既有关系和建立时间，不接受这两类关系覆盖。
4. 有效最终关系不含 `拆分` 时只允许一个所选后继；空集合是合法的完整关系，其他集合可以包含一种或多种直接前序关系。有效最终关系全部为 `归并` 时，必须指向至少两个不同前序。
5. `拆分` 策略要求至少两个显式所选后继；每个后继的有效最终关系必须恰好是一条指向同一前序的 `拆分`。显式选择集合必须等于事务完成后该前序的全部直接拆分后继，包括本次内容不变的已建立后继。
6. 单后继拆分、遗漏既有拆分后继、多个拆分前序、拆分与其他关系混合、重复后继以及没有已确认策略的多后继形状必须在任何写入前失败。新增拆分后继时，调用方同时选择原有全部后继和新候选；不能通过单后继重新挂接。
7. 有效最终关系中新引用的活动已建立目标作为直接前序归档；已经归档的合法直接前序保持归档。从完整集合移除的旧目标不会自动重新激活、删除或改变对齐状态。关系修订不授权改写已建立记录的判断语义。
8. 事务在写入前解析全部后继、计算有效最终关系、选择关系策略、验证状态和对齐选择、确定新增活动前序、检查未记录历史，并从最终记录组合验证完整关系图。全部预检通过后才依次归档新增活动前序、写入变化后的关系、建立候选、重建索引并读回严格检查。
9. 对可处理失败，事务尽力恢复命令前的全部受影响 Markdown 和索引组合；进程中断或恢复不完整时停止后续维护并按恢复手册处理。最终静态检查证明当前图闭合，但不证明历史上使用过哪一次命令。

## 维护不变量

1. 当前指令明确授权起草候选，或足以确认长期判断和维护范围时，可以在各自边界内直接维护；写入候选不等于确认方向。新增记录或改变状态前先告知用户将写入的判断和集合变化。
2. 写候选、编辑性修正和领域目录表维护可以直接修改权威来源；生命周期、对齐、归档和候选丢弃使用对应 CLI 命令。
3. 候选关系可以在审核前直接编辑；建立或修订正式关系使用“关系事务与完整集合”定义的 `evolve`，建立单个新候选时也可以使用 `activate` 的关系便捷入口。不能通过手工改写已建立 Markdown、逐边追加或多个不闭合命令拼接关系演进。
4. Git `HEAD` 只用于归档前判断决策路径是否已经进入已提交基线，不参与候选、建立、生效、对齐、索引成员或候选丢弃判断。当前 `HEAD` 中存在同一决策根相对路径即视为已经记录；文件内容、Git index 和工作区差异不改变该判断。尚无提交时，全部路径都视为未记录；丢弃已提交候选只删除工作区文件，不改写 Git 历史。
5. `evolve`、带关系的新候选 `activate` 或 `archive` 即将归档未记录路径时，首次调用暂停、返回 warning 且不写入；调用方判断后显式确认保留未提交历史，单候选后继演进也可以选择折叠。只有确认决策集合不在 Git 工作树内时才跳过预检；仓库发现或 `HEAD` 读取失败时停止且不写入。
6. `evolve` 只在显式提供 `--collapse-unrecorded` 时折叠一个活动、已建立且不在 Git `HEAD` 的中间前序，并且一次只能选择一个候选后继。折叠目标不能仍被其他记录引用；最终关系集合仍按来源关系、`--relation` 覆盖或 `--clear-relations` 解析，但空的最终关系集合必须由 `--clear-relations` 明确选择，不能从空来源关系推断。已归档目标只能是折叠记录原有的直接前序，CLI 不自动继承或合成关系。该归档目标限制只适用于折叠；普通 `evolve` 可以保留任意合法的已归档直接前序。非 Git 集合继续使用既有生命周期，不能在缺少版本证据时折叠。
7. 不使用统一关系事务时，先使用 `archive` 归档全部直接前序，再把完整关系集合写入候选并激活；不能只改变旧记录或只增加关系来表达新方向。归档预警仍需在动作前处理。
8. `activate` 审核并建立候选或重新激活已归档记录，`evolve` 统一建立或修订完整关系事务，`mark-aligned` 在完整方向成为当前事实并核对后建立基线，`archive` 退出当前依据并保留最后对齐状态，`discard` 只删除尚未建立且没有被引用的完整候选；候选即使已经进入 Git `HEAD` 也可以直接删除，不使用 `discard` 或通用删除动作重写已建立历史。
9. 状态命令完成后会更新查询投影；手工修改权威来源后运行 `sync-index --write`。任何情况下都不直接编辑派生索引。
10. 合法完整候选可以跨任务等待审核。严格 `check` 必须从源码发现并计数候选，对候选关系执行前瞻性结构检查，但不因为候选未进入正式索引、其关系未进入正式图或活动前序尚未归档而失败；候选结构不完整、状态组合非法、身份与索引冲突或前瞻性关系无效时仍然失败。
11. 无法确定的内容若会改变决策含义、生命周期、关系、建立时间或责任领域，保留现状并请求用户判断。

## 派生索引与查询

1. 索引从当前领域目录表和全部已建立 Markdown 完整生成，为 `list`、`show` 和 `trace` 提供持久查询快照；候选始终排除。`domains` 直接读取领域目录表，`candidates` 和 `show-candidate` 直接扫描源码中的完整候选，不改变正式索引。
2. 候选查询按文件容错：单条 Markdown 的结构、状态或关系非法时，跳过该文件、报告 warning，并继续返回其他合法候选；显式请求的目标自身非法时失败并返回目标诊断。决策根、根目录成员、领域目录表或领域目录布局非法属于集合级错误，查询失败且不返回部分集合。
3. 索引 metadata 提供完整领域定义；每条记录的领域由路径确定，不在 Markdown 或索引 state 中重复维护另一份领域字段。
4. 常规查询直接读取结构有效的持久索引，不在每次查询前遍历全部 Markdown 或重算源 revision；`show` 只额外读取目标正文。索引表达最近一次成功生命周期事务或同步后的集合状态。
5. 生命周期事务负责同步 Markdown 与索引；手工修改领域定义、成员、路径或原文后，调用方必须运行 `sync-index --write`，并在维护或验收前运行严格 `check`。
6. 索引缺失、损坏或陈旧时可以从权威来源重建；不能从索引反向补造领域、生命周期、时间、正文或关系。
7. 精确字段、合法值、版本和结构以 [decision-index.schema.json](decision-index.schema.json) 为准；同步、规范化和 revision 等通用机制不在本契约重复说明。

## 验证

1. `check` 机械验证领域目录、路径、Markdown 结构与状态组合、关系、索引结构、新鲜度和成员一致性，并报告源码中合法候选的数量；候选未进入正式索引本身不是成员错误。
2. Agent 另外检查记录门槛、领域选择、目的与理由质量、摘要和正文语义一致性、关系是否为直接前序、拆分后继集合是否覆盖前序长期含义，以及标记已对齐前是否已有完整当前事实证据。
3. 工具或索引故障、写入中断或普通诊断不足时，停止猜测并读取 [maintenance-recovery.md](maintenance-recovery.md)。
