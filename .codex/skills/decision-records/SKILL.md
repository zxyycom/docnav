# Decision Records

## 目标

在长期判断形成或拟议方向与既有判断冲突时，帮助 agent 恢复当前决定、区分当前基线与未来方向、判断相关工作如何使用这些方向、识别一次性例外与长期修订，并在记录粒度失效时重建可独立演进的决策边界，把完整待审方向和已经确认且值得回放的判断维护为可继续使用的决策记录。

决策记录保存“项目决定往哪里走、为何这样选择、它是当前基线还是未来方向、后续选择应如何受其影响”。`candidate` 表示记录结构和内容已经完整、可以审核，但尚未确认进入当前决策集合；`active` 表示判断已经确认并进入当前决策集合；`alignment` 区分已经成为当前事实的基线与尚未成为当前事实、供后续演进参考的未来方向。它不保存任务进度、执行日志或当前实现快照；代码、配置、规范和项目文档仍是当前事实来源，未对齐状态也不构成实施承诺、任务或授权。

## 内容 owner

1. 本文件面向 agent，承接触发后的读取路径、决策判断、动作选择和交付验收。
2. [decision-record-rules.md](references/decision-record-rules.md) 面向需要写入或结构维护的 agent，承接决策模型、内容边界、领域与身份语义、生命周期、关系、版本快照和维护不变量。
3. [decision-index.schema.json](references/decision-index.schema.json) 承接索引的精确机器结构；本文件和领域契约不复制字段顺序、版本、派生键或序列化细节。
4. `scripts/decision-records.mjs --help` 承接当前 CLI 参数；CLI 实现和校验承接精确输出、退出状态和索引操作细节。
5. [maintenance-recovery.md](references/maintenance-recovery.md) 只在 CLI 不可用、索引故障、写入中断或普通诊断不足时读取。

## 主动读取

1. 先读目标工作区指令和与当前任务直接相关的事实来源。
2. 按 `--root` 和可选的 `--decisions-dir` 定位决策集合；集合整体不存在时视为尚未初始化，不从 Git 状态推断决策是否存在或生效。
3. 日常恢复先运行 `list` 读取最近一次成功维护或同步后的索引快照。需要选择责任领域时运行 `domains`，需要完整理由时运行 `show`，需要理解演进关系时运行 `trace`。只有审核尚未建立的记录时才运行源码查询 `candidates` 和 `show-candidate`；普通查询不把候选混入正式索引结果。
4. 摘要足以完成当前判断时停止扩大读取；只有任务需要历史时才查询归档记录或完整关系图。
5. 相关活动决策尚未建立为当前基线时，完整读取决策并与当前事实来源比较，区分未来方向、当前事实和本次任务范围；若只有部分方向成为事实，再判断这些部分能否独立演进，而不是把整条记录直接归为部分对齐。
6. 只读恢复、冲突判断和对话中尚未写成完整记录的候选判断不加载领域契约；任何候选写入、状态变化、关系变化、领域变化、`pending` 决策快照构造或结构审阅前完整读取领域契约。
7. 只有工具、索引或中断写入不能通过普通 CLI 诊断处理时才读取恢复手册。

## 执行流程

### 1. 确定任务出口

1. 恢复、解释、检查或审阅已有决策时，只交付查询或审阅结果；没有维护授权时不扩大为写入。
2. 当前指令明确要求起草候选，并给出维护对象和影响范围时，可以写入完整 `candidate`，但不据此推断方向已经审核通过。只有当前指令也确认了完整方向及其对齐状态时才激活；任何写入前先告知将改变的判断和集合。
3. 普通工作中形成重要取舍时，在自然更新或交付阶段提出候选；只有继续任务必须先确定该取舍时才即时提出。
4. 长期含义、适用范围或被改变的责任边界仍不清楚时，只确认会改变记录结果的最小问题。

### 2. 恢复当前判断

1. 从 `list` 的领域、路径、生命周期、对齐状态和摘要定位相关记录。
2. 从完整记录的目的恢复长期结果，从背景恢复选择依据，从决策恢复采用方向及必须遵守的限制。
3. `active` 表示决策已经确认并进入当前决策集合；`active + aligned` 表示完整方向已经成为当前事实、通过核对并建立为持续基线，`active + unaligned` 表示已经确认但尚未成为当前事实的未来方向。`alignment` 始终作用于整条决策，不存在部分对齐状态；未对齐方向可以随后实施、修订、拆分或归档，不表示任务尚未完成，也不保证将来一定实施。
4. 对每条直接相关的活动决策判断它与当前任务的关系；同一任务可以同时遵守一条当前基线、把另一条未来方向作为输入，并实施第三条方向的一部分。每条决策使用前三类之一，并按需另外识别后三类维护结果：
   - 已对齐继续：遵守活动已对齐基线。
   - 未来方向输入：未对齐方向不是当前任务的交付或验收目标；选择方案时使用该方向，兼容性微调仍属于本类。
   - 实施未来方向：当前指令或工作制品已经把未对齐方向的全部或一部分明确纳入交付或验收目标。
   - 明确的一次性例外：按当前指令完成本次任务，说明例外范围，状态和历史不变。
   - 长期修订：形成新的完整候选和真实直接关系。
   - 一致性问题：多个当前基线互相冲突、多个未来方向互相冲突、已对齐记录与当前事实偏离，或当前动作无授权地违反活动决策；当前基线与未来方向之间仅因时间角色不同而存在的差异不属于冲突。
5. 已对齐记录发生事实偏离时不改回 `unaligned`；报告一致性问题。新的未来目标通过新决策表达。
6. 常规查询读取持久索引快照，不逐次证明全部 Markdown 新鲜度。手工修改来源、怀疑快照陈旧或准备维护时先运行严格 `check`，需要接受来源变化时运行 `sync-index --write`；不得用尚未同步的查询结果断言来源中不存在记录。

### 3. 提出候选决策

候选判断需要同时具备长期影响和回放价值。依次确认：

1. 它是否持续影响后续行为、责任边界、兼容性、风险处理或验收？
2. 缺少记录时，未来是否难以恢复为何采用当前方案？
3. 它是否是判断或取舍，而不是事实、任务、进度或执行结果？
4. 它是否能够作为一个整体独立修订、替代、归档和判断对齐？可能产生不同演进或对齐结果的判断分别记录。

当前指令明确要求起草候选时，复用该写入授权；完整候选只表示判断已达到语义审核门槛，不表示方向已经获准建立。当前指令没有授权写入时，只给出目的、背景、采用方向、必须长期遵守的限制和必要的直接关系，等待授权后再写入。当前实现差距留在当前事实来源，不作为决策正文中的专门结构保存。

尚未满足完整 Markdown 结构的内容只作为对话或 change 中的草稿，不写成决策候选。写入决策根的候选必须拥有稳定新身份、完整 frontmatter、摘要和三段正文；完整只表示它已经可以接受语义审核，不表示方向已经获准建立。

### 4. 选择动作

1. 既有活动已对齐基线适用时，按其方向与约束继续任务，不为普通执行创建新记录。
2. 未对齐方向不是当前任务的交付或验收目标时，把它作为方案选择输入：在同样满足当前要求、约束和验收标准，且不引入新的外部依赖、数据迁移或兼容性风险的方案中，优先选择兼容方向的方案。只有局部调整位于当前任务已授权修改的对象和责任边界内、不增加独立验收目标，且不引入上述额外风险时，才把它作为兼容性微调一并完成；否则不扩大实施范围。
3. 当前任务的交付或验收目标明确包含未对齐方向的全部或一部分时，按决策与当前事实实施。不可独立演进的局部落地仍使整条决策保持 `unaligned`；若不同部分本来可以分别修订、归档或对齐，说明记录过粗，应以闭合拆分建立多条后继并分别判断对齐，不能增加部分对齐状态。
4. 当前指令只形成一次性例外时，限定本次范围并保持决策集合不变。
5. 长期方向、理由或责任边界发生变化时，形成能够独立使用的新决策，并保存与直接前序的真实关系。
6. 多个活动已对齐基线互相冲突、多个活动未对齐方向互相冲突，或已对齐基线与事实偏离时，报告一致性问题；已对齐基线与未对齐方向的差异本身不是冲突，没有新的长期判断时不通过改写历史掩盖问题。

### 5. 维护记录

1. 完整读取领域契约，确认领域、稳定身份、记录内容、生命周期、关系和维护顺序。
2. 写好 `status: candidate`、`alignment: null`、`createdAt: null` 的完整候选后，先确认其中没有需要分别演进或对齐的多个判断，并把真实直接前序保存为候选的完整预期关系集合。候选可以继续修改或等待审核，但其关系在建立前不进入正式关系图；审核通过时再根据完整方向与当前事实的关系决定以 `aligned` 或 `unaligned` 激活，尚未成为当前事实的未来方向必须使用 `unaligned`。它会影响后续相关选择，但不自行创建实施承诺、任务、优先级或授权。
3. 已确认方向后来完整成为当前事实时，在逐项核对后标记为已对齐。
4. 建立或修订关系时使用 `evolve`，通过重复 `--successor <alignment=decision-path>` 显式选择完整后继集合。每个后继可以是候选或已建立记录：候选按调用方选择的对齐状态建立；已建立记录的对齐选择必须与现状一致，并且只能替换完整关系集合，正文、生命周期、对齐状态和建立时间保持不变。未提供关系覆盖时分别采用每个后继自身的完整关系；重复 `--relation` 是作用于全部所选后继的完整公共覆盖；`--clear-relations` 表示显式空集合。三种输入不能隐式追加或合并。
5. `activate` 仍是建立单个新候选的便捷入口。候选自身声明关系，或调用方显式覆盖、清空关系时，`activate` 把目标转换为单后继关系事务；重新激活已归档记录时保留既有关系，不借激活动作修订历史关系。所有关系事务都先验证完整最终组合，再归档新增活动前序、写入变化后的完整关系、建立候选、重建索引并读回检查。
6. 关系策略决定一次事务允许的成员和拓扑。普通关系只选择一个后继；纯 `归并` 至少包含两个不同前序。一个粗决策需要重建为多个独立判断时，先准备至少两个自包含后继，逐个保存指向同一前序的唯一 `拆分` 关系，核对完整后继集合没有静默遗失前序含义，再由一次 `evolve` 显式选择全部既有和新增直接拆分后继。不能用单后继追加、遗漏既有后继或混合关系拼接拆分；多前序到多后继的重组等待现实实例，不推测协议。
7. 若事务即将归档的记录尚未进入 Git `HEAD`，命令先暂停且不写入；判断其是否具有长期回放价值后，显式选择保留未提交历史，或只在单候选后继场景折叠一个中间前序。普通 `evolve` 可以保留任意合法的已归档直接前序；折叠时，已归档最终目标只能是被折叠记录原有的直接前序，且不会自动继承或合成上游关系，空的最终关系集合必须显式清空。存在分叉、多层中间链、其他引用或最终直接关系不清楚时保留现场并请求判断；`discard` 仍只用于不再需要的尚未建立候选。候选是否已经进入 Git `HEAD` 不影响删除工作区文件，Git 历史本身不会被改写。
8. 内容或领域来源发生编辑性变化时同步索引；不得直接修改派生索引来制造决策状态。

### 6. 构造待提交决策快照

1. 只有调用方明确要让一个或多个 `filesystem` 决策变化进入下一版本时才运行独立的 `stage <decision-path...>`；路径必须逐项显式选择，并共同形成一个合法决策集合。重命名同时选择旧路径和新路径，不从关系、差异或命令历史推断选择集。
2. `stage` 以当前 `revision` 决策集合为基线，只叠加所选路径在 `filesystem` 中的状态：新增或修改读取磁盘内容，删除由路径仍在 `revision` 但已不在磁盘表达。既有 `pending` 决策变化和未选择的其他磁盘变化都不参与目标构造。
3. 命令从同一目标来源重建并验证完整索引后，整体替换 `pending` 决策范围。最后一次成功调用决定该范围的完整内容；范围外既有 `pending` 内容和整个 `filesystem` 保持不变。生命周期命令仍直接读写磁盘决策文件，不读取、判断或写入 `pending`。
4. 指定路径、候选、领域或关系不能形成合法目标，版本管理环境不可用，或目标构造期间 `revision` 或受控 `pending` 前提发生变化时，按诊断修正选择或重新读取后重试；这些失败不接受部分结果。若工具报告 `pending` 范围恢复不完整，停止后续维护并保留诊断，不继续猜测或覆盖。
5. 当前分发实现只在可用的 Git 工作区中提供 `stage`。调用方只依赖 CLI 暴露的 `revision`、`filesystem`、`pending` 和项目路径语义，不解析或透传 Git 内部值。

### 7. 验证与交付

1. 确认候选包含完整到可审核且值得长期回放的方向，活动记录只包含已经确认的判断；两者的目的、背景、采用方向和长期约束互相一致。
2. 标记已对齐前，将完整决策与当前事实来源逐项核对；只有部分内容对齐时，确认它是不可独立演进的局部落地还是需要闭合拆分的粒度问题。保持未对齐时，从同一比较恢复未来方向与当前事实的差异，并说明它对本次任务的实际影响。
3. 维护结束时运行严格 `check`。合法完整候选可以继续等待审核，检查会发现并计数但不会把它视为索引缺失；结构不完整、状态组合错误或与正式集合冲突的候选仍然阻断验收。中间命令的成功或 warning 不替代最终检查。
4. 写入时说明新增、修订、归档或对齐变化及验证结果；只读恢复时说明适用决策、当前分类和结果边界。

## CLI

从 skill 目录运行，或使用脚本绝对路径：

```text
node scripts/decision-records.mjs <command> [options] --root <resolution-root>
```

| 命令 | Agent 使用效果 |
| --- | --- |
| `domains` | 查看可选领域及其责任边界。 |
| `candidates` | 从 Markdown 源发现结构完整、尚未建立且不进入正式索引的候选；跳过单条非法源码并报告 warning，集合结构非法时失败。 |
| `list` | 从持久索引按领域、生命周期或对齐状态恢复紧凑定位信息。 |
| `show` | 从索引定位并读取一条决策的完整 Markdown。 |
| `show-candidate` | 从源码读取一条完整候选，供激活或丢弃前审核；其他单条非法源码只产生 warning，目标自身或集合结构非法时失败。 |
| `trace` | 查看一条决策的直接演进链路。 |
| `check` | 严格验证整个决策集合及派生索引。 |
| `sync-index --write` | 从当前领域定义和已建立记录重建查询索引。 |
| `stage` | 从当前 `revision` 与显式选择的 `filesystem` 决策构造完整、一致的 `pending` 决策快照，不修改磁盘决策集合。 |
| `activate` | 审核并建立一个完整候选，同时选择对齐状态和写入建立时间；新候选可以使用自身关系、完整公共覆盖或显式空集合进入单后继关系事务。重新激活已归档记录时保留原建立时间和关系。 |
| `evolve` | 显式选择一个或多个候选或已建立后继，按完整最终关系集合校验策略，并在一次可恢复事务中处理前序归档、关系替换、候选建立和索引重建；单候选后继还可以显式折叠一个未记录中间前序。 |
| `mark-aligned` | 在完整方向成为当前事实并通过核对后建立当前基线。 |
| `archive` | 让活动决策退出当前依据并保留最后对齐状态与历史；目标尚未进入 Git `HEAD` 时先暂停，要求显式确认是否保留。 |
| `discard` | 删除尚未建立且可安全丢弃的完整候选，不因该文件已经进入 Git `HEAD` 而保留。 |

`evolve` 是关系建立、完整修订和闭合多后继演进的统一入口。`activate` 只为建立一个新候选保留便捷形式；它在候选带有关系输入时进入同一个事务核心，不能绕过关系策略。完整参数和互斥条件以命令帮助为准。

`stage` 是独立的版本快照命令，不是生命周期选项；`activate`、`evolve`、`archive`、`mark-aligned` 和 `discard` 均不提供 `--stage`。

具体参数使用对应命令的 `--help`；索引的精确字段、版本和格式查看相邻 JSON Schema。写命令执行前读取领域契约；手工修改 Markdown 后先同步或严格检查，不从索引反向补造权威来源。

## 完成标准

1. 已恢复所有与当前任务直接相关的活动决策，逐条判断应遵守当前基线、把未来方向作为输入还是实施未来方向，并按需识别一次性例外、长期修订或一致性问题。
2. 新候选只保存具有长期影响和回放价值、内容完整到可审核、能够作为整体独立演进和判断对齐的方向；候选关系表达完整预期集合，但只有审核确认后才进入正式关系图并成为活动记录。粗决策拆分后的完整后继集合没有静默遗失前序含义。
3. 决策与当前事实来源的关系已经核对；对齐状态准确区分当前基线与未来方向，没有用部分状态掩盖粒度问题，也没有代替事实检查、自行扩大任务范围或让相关工作忽略未对齐方向。
4. 所有写入遵循领域契约；关系事务显式选择完整成员并按完整最终关系校验，合法候选能够通过源码查询被发现并保持在正式索引外，已建立记录与派生索引一致，派生索引没有被当作事实源。
5. 使用 `stage` 时，显式选择、目标领域目录表、全部目标 Markdown 与完整索引来自同一目标来源；`pending` 决策范围外内容和 `filesystem` 未被改变。
6. 严格 `check` 返回成功；无法运行时按恢复手册说明尚未证明的边界。
