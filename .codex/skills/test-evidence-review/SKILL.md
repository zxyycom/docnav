# Test Evidence Review

## 目标

审查测试是否具有稳定、可证伪且由当前行为 owner 支持的证明目的，并核对其可观察
信号、可靠性、证据独立性和维护价值。

项目声明语义 Case 账本时，Case 连接行为 owner、证明内容和项目当前测试证据；
Case 的边界由共同的 owner 契约和可观察结果决定，而不是测试函数数量。项目另行
声明 Topic 时，Topic 只用于有界查询，不替代行为 owner 或 Case 身份。没有账本
时，仍执行测试质量审查，但不创建 Case、Topic 或其它持久化机制。

**不得仅为使某段测试能单独进入账本而拆分测试。**

## 能力边界

项目文档拥有测试策略、行为契约，以及项目实际采用的 Case 存储、Topic、查询和
严格检查规则；项目源码与 runner 拥有当前测试事实。本 skill 只提供能力感知的
评审方法，不提供项目路径、runner adapter、schema、CLI runtime 或持久化格式。
项目规则与本 skill 不一致时，以项目 owner 为准。

开始前按以下顺序获取项目上下文：

1. 读取项目文档导航、测试策略和相关行为 owner，确认当前契约与自动化测试义务。
2. 识别项目明确声明的能力，不能从本 skill 推定：
   - 有 Case 账本时，读取账本 owner 的对象、存储、查询和修改规则。
   - 有 Topic 时，读取 Topic 的受控值与查询规则。
   - 有完整性 wrapper 时，读取其支持范围、闭合条件和失败语义。
3. wrapper 声明能证明完整集合时，修改前运行完整检查；wrapper 只支持部分范围时，
   只对该范围下结论并说明全局未证明。没有 wrapper 时，不声称全局完整。
4. 项目没有 Case 账本时，直接评审目标测试；不要临时发明通用存储、runner
   profile、Topic 或自动生成 Case。

lint、类型检查、schema、build、fixture、helper、hook、mock 和测试步骤通常是工程
校验或实现构件，不因存在于验证链就自动成为测试实体或 Case。

历史 Case、事故、回归记录、旧映射和变更文档只提供风险、迁移或代表输入线索。
它们本身不构成当前 coverage 缺口，也不要求为恢复历史账本而新增产品测试；是否
补测试由项目测试策略和行为 owner 决定。项目声明当前实体映射时，缺少当前直接
实体的历史语义同样不进入当前闭合范围。

## 审查顺序

1. 按“能力边界”的顺序读取项目 owner，识别 Case、Topic 和 wrapper 能力。
2. 项目声明完整性 wrapper 时运行起点完整检查；项目 owner 要求全树闭合时，Git
   diff 只能缩小人工审查范围，不能替代完整检查。
3. 项目声明 Case 账本时，按账本 owner 提供的读取方式定位相关 Case 和映射；只有
   owner 同时声明查询入口时才执行查询，只有声明 Topic filter 时才按 Topic 查询。
   没有账本时跳过全部账本操作，直接读取目标测试和当前 diff。
4. 对新增或变化的测试判断：
   - **契约背景**：对应哪个稳定 requirement 或边界。
   - **证明信号**：失败是否能指向该契约失效。
   - **可观察性**：是否断言调用方可见的返回值、错误、状态、交互或资源结果。
   - **可靠性**：fixture、mock、时序、随机性和环境是否稳定。
   - **证据独立性**：预期值是否独立于被测实现。
   - **维护价值**：证明增量是否值得运行与维护成本。
5. 按项目能力分支：
   - 有 Case 账本时，先尝试关联已有 Case；只有 owner 契约或可观察结果确实独立时
     才新增或拆分。项目要求纳入账本但无法形成有意义 Case 的测试，应合并、删除
     或按项目规则移出账本，不能用模板 Case 消除缺口。
   - 没有 Case 账本时，直接依据第 4 步决定保留、收窄、合并或删除测试，不增加
     账本工作。
6. 运行目标测试、项目明确要求的严格检查和范围匹配的工作区验证。

## 账本项目的 Case 门槛

本节只适用于项目 owner 已声明语义 Case 账本的情况；没有账本时跳过。一个可维护
的 Case 应具备：

1. 稳定身份，不随机械测试名称变化。
2. 一个真正拥有全部证明内容的当前行为 owner。
3. 至少一项可证伪、调用方可观察的证明内容。
4. 项目账本要求当前实体映射时，至少一个当前实体作为执行证据。
5. 项目声明受控 Topic 时，属于一个合法 Topic；Topic 只用于查询，不承担行为
   所有权。

Case 不是完整契约文档，也不是测试源码摘要。只复述函数名、AST match、实现步骤，
或写成“测试稳定契约”“结果可观察”等模板，不能解释测试为何值得存在。项目 owner
声明的 Case 字段、映射、Topic 和闭合条件必须全部满足，不能因本 skill 保持泛用
而降级。

## 结构变化

- **rename**：先确认测试目的是否连续；有 Case 账本时保留连续 Case ID，并按项目
  规则更新映射。
- **split**：按实际证明目的分配新测试；有 Case 账本时，只有目的也分裂才拆 Case。
- **merge**：测试合并不自动合并证明目的；有 Case 账本时，一个测试可以按项目
  规则继续支持多个 Case。
- **delete**：先确认删除后的证明边界；有 Case 账本时同步相关 Case，并按项目规则
  处理失去当前证据的 Case。
- **正文变化**：即使测试身份未变，也要重读 owner 和断言；有 Case 账本时还要
  重读相关 Case，不能把映射闭合误当成语义仍然成立。

## 完成标准

1. 目标测试的当前行为 owner、证明信号、可观察性、可靠性、证据独立性和维护价值
   已经审查。
2. 项目声明 Case 账本时，变化 Case 满足其 owner、内容、映射和存储规则；项目
   声明 Topic 时，相关 Case 满足 Topic 规则。
3. 项目声明完整性 wrapper 时，已在其支持范围内通过完整检查；wrapper 只支持部分
   范围或不存在时，结论没有越过已证明范围。
4. rename、split、merge、delete 的语义连续性已经处理；有账本时没有靠机械生成
   或机械拆分填补账本，没有账本时没有临时发明账本机制。
5. 历史材料只作为审计输入；没有把历史语义误报为当前 coverage 缺口或本次产品
   测试义务。
6. 目标测试、项目明确要求的严格检查和范围匹配验证已经通过；无法证明的完整性或
   语义边界已明确说明。
